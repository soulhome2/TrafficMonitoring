## 1. Краткое резюме

- **Готовность спецификации — около 40 %** для старта разработки вертикального решения. Функциональная часть по видеоаналитике проработана хорошо (≈ 75 %). Продуктовая часть, источники данных кроме видео, архитектура данных и экономика почти отсутствуют (≈ 10–20 %).
- **Главный риск 1 — не определена граница с ИнтеллектХ.** Спецификация описывает самостоятельную платформу со своим приёмом видео, архивом, пользователями и аутентификацией (раздел 3, FR-SRC-04, FR-ACC-05). Для вертикали ИнтеллектХ это, скорее всего, дублирование функций базового продукта `[assumption]`.
- **Главный риск 2 — нет продуктовой рамки.** Нет формулировки проблемы клиента, бизнес-метрик эффекта, персон и сценариев по сегментам. Пять сегментов заказчиков с разными задачами покрыты одним набором функций, рассчитанным на муниципалитет и оператора дорог.
- **Главный риск 3 — единственный источник данных — видео.** Нет детекторов транспорта, GPS/ГЛОНАСС-треков, данных операторов связи, погоды, плановых событий, расписаний общественного транспорта. Нет стратегии на случай деградации источника. Это противоречит заявленному ограничению «доступные источники данных».
- **Главный риск 4 — архитектура не подтверждает нефункциональные требования.** Масштабируются только серверы обработки (NFR-02). Ядро, хранилище временных рядов, очереди и отказоустойчивость ядра не описаны, поэтому доступность 99,5 % ничем не обеспечена. API без контракта и версионирования (FR-INT-02).
- **Главный риск 5 — нет экономики.** Не посчитаны стоимость видеопотока (лицензия SDK, GPU, хранение полного архива), цена для клиента и KPI продукта.

## 4. Чек-лист «Definition of Ready»

**Продукт**

- [ ] Определены KPI продукта и модель монетизации (CR-40, CR-41).

- [ ] Зафиксирована граница «ИнтеллектХ / вертикаль» (CR-42).
- [ ] Описаны варианты развёртывания и разделение «периферия / центр» (CR-31).

- [ ] Стратегия деградации источника и флаги качества данных (CR-08).

## 5. Предложения по улучшению

Порядок — по приоритету.

1. **Определить границу с ИнтеллектХ и переписать архитектуру от неё** (CR-42, CR-03, CR-43). Таблица «функция → ИнтеллектХ / вертикаль / новая разработка» сократит объём разработки и снимет противоречие с контекстом продукта. Вероятно, видеопотоки, архив, пользователи и часть событий уже есть в базовом продукте `[assumption]`.
2. **Добавить продуктовую рамку и MVP** (CR-01, CR-02, CR-04, CR-51). Одна страница «проблема → сегмент → эффект → MVP → критерии пилота» до любых новых функций. Рекомендуемый первый сегмент `[assumption]`: муниципалитет / ЦОДД — спецификация уже ближе всего к нему.
3. **Описать архитектуру данных и варианты развёртывания** (CR-31, CR-32, CR-27, CR-26). Стриминг между серверами обработки и ядром, хранилище временных рядов, объектное хранилище, профили нагрузки. Без этого NFR не проверяемы.
4. **Сделать интеграции и экспорт продуктовыми, а не проектными** (CR-16, CR-12, CR-34). Стандарты DATEX II, NTCIP, OGC; экспорт в форматы PTV Visum / Vissim, SUMO, Aimsun; OpenAPI с версионированием. Это закрывает сценарии планировщиков и девелоперов без собственного моделирования.
5. **Добавить реестр источников данных и стратегию качества данных** (CR-06, CR-08, CR-28). Даже если MVP работает только на видео, реестр фиксирует путь расширения, а флаги качества и правила заполнения пропусков нужны уже для первых отчётов.
